# Computation Model Specification

## Overview

A computation represents an isolated, deterministic execution request submitted to the Developer Computation Cache (`dcc`). The computation model formally defines the complete set of parameters, constraints, and declarations required to compute an immutable `CacheKey` and safely restore outputs.

## Formal Structure

```text
Computation
    ├── schema_version: u32
    ├── operation: String
    ├── command: String
    ├── args: Vec<String>
    ├── inputs: Vec<InputFile>
    │     ├── path: String (normalized forward slashes)
    │     ├── digest: Digest (SHA-256)
    │     ├── size: u64
    │     └── is_executable: Option<bool>
    ├── outputs: Vec<OutputFile>
    │     ├── path: String (normalized forward slashes)
    │     └── required: bool
    ├── env: BTreeMap<String, String> (explicitly declared relevant environment)
    ├── platform: PlatformConstraints
    │     ├── os: String
    │     ├── arch: String
    │     └── target: Option<String>
    ├── tool: Option<ToolIdentity>
    │     ├── name: String
    │     ├── version: Option<String>
    │     └── digest: Option<Digest>
    ├── policy: CachePolicy (ReadWrite, ReadOnly, WriteOnly, Bypass, ForceRecompute)
    ├── metadata: BTreeMap<String, String> (arbitrary caller tags/context)
    └── working_dir: Option<String>
```

---

## Field Specifications

### 1. `operation`
- Unique identifier for the category or task of computation (e.g. `codegen`, `build`, `transpile`, `test`, `lint`, `format`).
- Required; cannot be empty.

### 2. `command` & `args`
- The executable name/path and its exact sequence of arguments.
- Arguments preserve order strictly.
- Executed directly via OS process APIs (`std::process::Command`), never concatenated into raw shell strings.

### 3. `inputs` (Declared Input Files & Hashes)
- Declared input files with their content digests (SHA-256) and sizes.
- Paths are canonicalized to forward slashes (`/`) and sorted lexicographically.
- Symlink loops and illegal parent escapes (`../`) are strictly forbidden.

### 4. `outputs` (Declared Output Files)
- Expected artifacts generated by the computation.
- Must fall within the designated workspace boundary (path traversal checks enforced).

### 5. `env` (Environment Variable Rules)
- **Principle**: Do NOT include all ambient system environment variables. Ambient environment variables (like `PATH`, `TMP`, `USER`, `HOSTNAME`, random process IDs) cause unnecessary cache key fragmentation.
- **Rule**: Only explicitly declared relevant environment variables (e.g., `NODE_ENV`, `RUST_LOG`, `GENERATOR_VERSION`, `OPT_LEVEL`) are recorded and hashed into the computation identity.
- Stored as a `BTreeMap<String, String>` to guarantee deterministic lexicographical sorting.

### 6. `platform` (Platform Constraints)
- Captures system dimensions where cross-compilation or OS-specific ABI matters:
  - `os`: e.g., `windows`, `linux`, `macos`
  - `arch`: e.g., `x86_64`, `aarch64`
  - `target`: optional target triple (e.g., `x86_64-pc-windows-msvc`)

### 7. `tool` (Tool Identity & Version)
- Identifies the executable binary producing the output.
- Contains the tool name, optional semantic version string (e.g. `1.80.0`), and optional tool binary content hash.

### 8. `policy` (Cache Policy)
- Defines the caching behavior for execution:
  - `ReadWrite` (default): Lookup cache on start; store on success.
  - `ReadOnly`: Lookup cache on start; do not write back if miss.
  - `WriteOnly`: Always execute; store result to cache.
  - `Bypass`: Do not lookup or store.
  - `ForceRecompute`: Force fresh execution and overwrite previous cache entry.

### 9. `metadata` (Computation Metadata)
- Caller-provided descriptive attributes (e.g., `git_commit`, `ci_job_id`, `author`).
- Included in the cache entry record for auditing and inspection.

## Canonical Normalization & CacheKey Derivation

To guarantee that equivalent computations produce identical keys regardless of platform differences:
1. All file paths are normalized with `/` separators.
2. Inputs and outputs are sorted lexicographically by normalized path.
3. Environment variables and metadata are sorted by key.
4. The normalized struct is serialized to deterministic canonical JSON.
5. `SHA-256(canonical_json)` yields the unique `CacheKey`.
