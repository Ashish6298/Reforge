1. OBJECTIVE & SCOPE
--------------------------------------------------------------------------------
Milestone 9.2 requires instrumenting the Developer Computation Cache engine with
granular timing metrics across the entire computation and cache lifecycle:
  - computation execution time
  - cache lookup time
  - cache restore time
  - cache store time

And calculating:
  - time saved

2. ARCHITECTURE & IMPLEMENTATION
--------------------------------------------------------------------------------
1. Data Model (`crates/cache-core/src/entry.rs`):
   - Created `TimingMetrics` struct:
     * `execution_time_ms`: u64 (duration of subprocess execution)
     * `lookup_time_ms`: u64 (duration spent querying entry index/metadata)
     * `restore_time_ms`: u64 (duration spent retrieving and writing outputs from CAS)
     * `store_time_ms`: u64 (duration spent hashing, writing CAS objects and storing entry)
   - Added calculation method:
     `TimingMetrics::calculate_time_saved_ms(&self) -> u64`:
     Calculates `execution_time_ms.saturating_sub(lookup_time_ms + restore_time_ms)` on cache hit.
   - Integrated `timings: TimingMetrics` into `ExecutionMetadata` and `ExecutionResult`.

2. Engine Instrumentation (`crates/cache-runner/src/engine.rs`):
   - `lookup_time_ms`: Measured via high-precision `Instant::now()` around `get_entry(&key)`.
   - `restore_time_ms`: Measured via `Instant::now()` around `OutputRestorer::restore_entry`.
   - `execution_time_ms`: Measured accurately from process launch to completion in `ProcessExecutor`.
   - `store_time_ms`: Measured via `Instant::now()` around all CAS blob storage operations and entry write.

3. Serialization & Backward Compatibility:
   - Decorated `timings` field with `#[serde(default)]` in `ExecutionMetadata` to ensure seamless backward compatibility with existing cache records.
