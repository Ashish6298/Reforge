1. OBJECTIVE & THREAT MODEL
--------------------------------------------------------------------------------
Milestone 14.1 requires that DCC treat cached artifacts as potentially dangerous data.
A caching system must never blindly trust stored objects, metadata, or output manifests.

Three Critical Attack Vectors Analyzed & Mitigated:
  1. Malicious / Poisoned CAS Object:
     - Threat: An attacker or disk bitrot alters bytes in `.dcc_cache/objects/xx/<digest>`
       to inject malicious trojan binaries into downstream developer workspaces.
     - Defense: Cryptographic pre-restoration verification (`CasStorage::verify_object`)
       and post-materialization digest check. On mismatch, the compromised CAS blob
       is quarantined with `.corrupted` extension, restoration aborts immediately,
       and safe fallback execution is triggered.
  2. Malicious Metadata / Key Spoofing:
     - Threat: An attacker crafts a forged `.json` entry in `.dcc_cache/entries/xx/`
       claiming a legitimate key (e.g. standard compiler invocation) but embedding
       a malicious computation command (`rm -rf /` or malicious binary).
     - Defense: `entry.verify_identity()` executes canonical SHA-256 key calculation
       over the embedded `Computation` model and compares against `entry.key`.
       `Cache::restore` and `RunnerEngine` enforce `verify_identity()` prior to
       extracting any files.
  3. Tampered Output Manifest & Atomic Staging Rollback:
     - Threat: Metadata declares forged output digest or size, attempting partial or
       corrupted extraction into target workspace.
     - Defense: Restoration stages outputs into temporary `.tmp_restore_<nonce>` files.
       Digests are verified from reader stream before atomic rename. If validation fails,
       temporary files are wiped and the target workspace path is never overwritten.
