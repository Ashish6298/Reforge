1. EXECUTIVE SUMMARY & OBJECTIVE
--------------------------------------------------------------------------------
Milestone 6.2 verifies and guarantees concurrent write safety across the Developer
Computation Cache (DCC). Two or more processes or threads writing the exact same
or distinct objects simultaneously must never corrupt storage, produce partial files,
or leak orphaned resources.

Core Invariant:
"Two processes writing the same object must never corrupt it. Use atomic object
creation and/or locking."

--------------------------------------------------------------------------------
2. ARCHITECTURAL DESIGN & INVARIANTS
--------------------------------------------------------------------------------
- Two-Stage Atomic Write Pipeline:
  All CAS object storage operations (`store_object_bytes`, `store_object_from_file`)
  and CacheEntry commits (`store_entry`) follow a strict atomic pipeline:
    1. Allocate a unique random nonce temporary file in `.cache/tmp/<nonce>.tmp`.
    2. Stream data to the temporary file via `BufWriter`.
    3. Flush buffers and execute `dst.get_ref().sync_all()` (`fsync`) to flush
       operating system write caches to durable physical media.
    4. Execute atomic rename (`fs::rename`) into the final sharded path
       (`.cache/objects/ab/abcdef...` or `.cache/entries/12/123456...json`).
    5. In case of racing creation where destination already exists, cleanup the
       temporary file without throwing an error if the final file is intact.

- Collision Isolation & Deduplication Race Safety:
  * When multiple processes compute the exact same output bytes simultaneously,
    both write full temporary files and attempt to rename them into the same CAS path.
  * The target file is either created or atomically overwritten with identical bytes.
  * No thread can ever read a half-written file because reads only target the final
    renamed path after `fsync`.
  * Temporary files from competing writers are cleanly removed, leaving the `.cache/tmp/`
    directory completely empty.

- Concurrency Lock & Process Coordination:
  * High-level computation runs are coordinated via `ComputationLock` using OS-level
    advisory file locks (`fs2`), ensuring atomic execution handoffs.
